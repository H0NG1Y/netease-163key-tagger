### P1-1 —— `bitrate` 字段语义错误：42 个 FLAC + 4 个 MP3 写的是云端 MP3 档位，不是本地文件位率

**现象**

163key 里的 `bitrate` 字段，对**全部 42 个 FLAC** 都写成 `320000`（个别 `320001/320002`），而这些文件作为无损音频的真实位率是 **797 000 – 1 835 000 bps**，低了 3–5 倍。
另外 **4 个 MP3** 声明 `320000`，但文件首帧帧头是 **128 kbps**：

| 文件 | 写入 bitrate | 文件真实位率 |
| --- | --- | --- |
| `周杰伦 - 七里香.flac` 等 42 个 FLAC | 320000 | 797k – 1835k（无损） |
| `Michita - Cry For Me (feat. Ami).mp3` | 320000 | **128000** |
| `Valentin - Unchanged Mind.mp3` | 320000 | **128000** |
| `suhmeduh - Phone Kisses.mp3` | 320003 | **128000** |
| `郑润泽 - 瞬.mp3` | 320000 | **128000** |

**为什么这是缺陷（语义判定依据）**

1. 社区事实标准 `163marker` 的源码（`probe/ref/163marker-core.py.txt` **L80**）写的是 `'bitrate': audio.info.bitrate` —— mutagen 的 `audio.info.bitrate` 就是**本地文件的位率**。这是该字段唯一有据可查的权威出处。
2. 官方真实样本恰好本地与云端都是 320k，单看它分不出语义；但 163marker 的写法、以及「对 FLAC 也一样赋值」这一事实，共同指向语义应是**本地值**。
3. 反过来看：给无损 FLAC 标 320 000 bps，在任何一种解释下都不成立——它既不是本地值，也不是「该曲最高可用档位」（云端有 `sqMusic.bitrate = 885246`）。

**根因（已定位到代码，仅上报不修）**

`lib/netease-api.mjs` 的 `bitrateOf()`（L638–L652）：匿名接口拿不到无损档码率时会 `return 320000`。
`apply.mjs` 第 279 行调用 `to163Meta` 时**只传了 `format` 与 `localDurationMs`，没有传 `bitrate`**：

```js
meta = api.to163Meta(detail, { format: rec.format, localDurationMs: rec.durationMs });
```

而 `notes/api.md` §7 自己写着「建议 flac 用本地容器/流信息推算」——建议写了，但没接上。项目里其实已经有本地码率读取器（`probe/_audioinfo.mjs` 的 `readAudioInfo()`，FLAC 读 STREAMINFO、MP3 读帧头），只是没有接入写入链路。

**最小复现**

```
node verify/06-metadata-fidelity.mjs
# 期望看到：FAIL F3a … 42 个不符；FAIL F3b … 4 个 MP3

node verify/_probe-bitrate-truth.mjs
# 逐条摊开三条证据：163marker 源码 / 官方样本 / 42 个 FLAC 的声明值 vs 真实值
```

**影响评估（为什么是 P1 不是 P0）**

`notes/api.md` §6.2 用 `dbTrack`（7172 行）实测证明客户端曲库模型里 `"bitrate"` 出现 **0 次**，即客户端不拿这个字段做任何本地判断。所以它不会导致「认不出歌」，属于**元数据不准确**而非**功能失效**。但它是写给客户端看的描述性字段，长期看会误导（例如将来某个按位率选流的逻辑）。

### P1-3 —— `蒋孜怡,岳燃 - 拼图爱.mp3` 是漏匹配（本可安全写入却未写）

**现象**

该文件没有 163key，但云端存在**完全匹配**的条目：

```
2655850235  拼图爱  蒋孜怡(31364543)/岳燃(29938303)  《拼图爱》(id 256713173)  151276ms
2659361593  拼图爱  蒋孜怡(31364543)/岳燃(29938303)  《拼图爱》(id 256713173)  151276ms   ← 与上一条完全同形（云端重复条目）
```

本地：`TITLE=拼图爱 / ARTIST=蒋孜怡;岳燃 / ALBUM=拼图爱 / 151320ms`。
歌名 ✅ 歌手 ✅ 专辑 ✅ 时长 Δ44 ms ✅ —— 四项全中。

**为什么没写**：两个候选打分完全相同（score = 1.0），被 `pickBest` 判为 `ambiguous: true`，于是 confidence 降为 medium，默认不写。

这在「宁可漏写不可写错」的策略下是**可辩护的保守**——两个条目除了 id 之外完全一样，写哪个都无法从元数据上区分。而实际上这两个 id 指向同一个专辑的同一首歌（同 albumId、同 pic、同时长），写任意一个都不算错。

**定性**：不是数据错误，是**覆盖率损失**。57 个文件里应能写 53 个，实际写了 52 个。

**最小复现**

```
node verify/_probe-unwritten.mjs
```

### P1-4 —— `一路向北` 两个文件：专辑标签与曲库不符，导致无法可靠匹配（可辩护，但值得记录）

`周杰伦 - 一路向北.flac` 与 `.mp3` 的本地专辑标签是《**J III MP3 Player**》，而云端不存在这个专辑名；这首歌在曲库里以《11月的萧邦》(185924, 295692ms) 和《Initial J》(185948, 297000ms) 两个版本存在。

- flac 本地 294240ms：距 185924 差 1452 ms，距 185948 差 2760 ms，两者都在 3s 容差内
- mp3 本地 295732ms：距 185924 差 40 ms，距 185948 差 1268 ms

### P2-1 —— FLAC 写入路径总是返回 `in-place` 而非 `noop`（重复运行会无谓落盘）

**现象**：对**内容已经完全正确**的 52 个交付文件调用 `write163Key`：

| 格式 | dryRun/real 策略 | 字节是否变化 |
| --- | --- | --- |
| MP3（10 个） | `noop` / `noop` | 不变 ✅ |
| FLAC（42 个） | `in-place` / **`in-place`** | 不变 ✅（内容幂等成立） |

即：**内容层面幂等成立**（sha256 恒定，这是硬要求），但 FLAC 路径每次都会真的开文件写一遍，并对外报告 `changed: true`。

**根因**：`lib/tags.mjs` 的 `writeFlac()` 没有「新 Vorbis comment 与旧的逐字节相同就返回 noop」的短路判断；`writeMp3()` 有（`if (found.text === keyText) return { changed: false, ... }`）。

**影响**：
1. 重复跑 `apply.mjs apply --write` 会对全部 42 个 FLAC 做无谓写盘。
2. `apply.log.json` 里无法区分「本次新增」与「本来就有」——审计时会误判「写了 42 个」。
3. 每次写盘都有一个极小的中断风险窗口（虽然 in-place 且长度相同，风险远低于 rewrite）。

**最小复现**

```
node verify/04-structure-idempotency.mjs
# 期望看到：OK「MP3 路径…全部返回 noop」；OK「FLAC 路径…非 noop 42/42」
node verify/_probe-idempotency-report.mjs
# 明确打印两种格式的策略分布与字节变化
```

### P2-2 —— `mp3DocId` 有 50/52 是合成占位值，不是云端 CDN 对象的真实 md5

**现象**：我用项目里 `md5FallbackFor()` 的公式 `md5("netease-163key-tagger|<musicId>|<format>")` 逐条复算，52 个里有 **50 个命中**：

| 命中配方 | 数量 | 说明 |
| --- | --- | --- |
| `synthetic(meta.format)` | 8 | 最终容器是 mp3，按 mp3 算 |
| `synthetic(mp3)` | 42 | 最终容器是 **flac**，却按 `mp3` 算（因为 detail 记录的 format 恒为 mp3） |
| 非合成 | 2 | `阴雨天 - 和你的照片还留着.mp3`、`颜人中 - 我只能离开.mp3` |

而官方真实样本的 `mp3DocId = cde6b150f488f81c8f0d9b374d2fe2fb`，既不等于本地整文件 md5，也不等于音频区 md5——它是**云端 CDN 对象的 md5**，需要 `player/url` 接口（登录 + 版权）才能拿到。本批 52 首里，匿名请求 `player/url` 全部返回 `code 404 / -110`，拿不到真值。

**定性**：这是**已知且被文档化的降级**（`notes/api.md` §A3 用 `dbTrack` 里 `"docId"`/`"mp3DocId"` 各 0 次 证明客户端不比对这个字段），并且合成值保证了「32 位小写 hex 形状合法 + 每首唯一不串台」。**不算功能缺陷**，但必须如实记录：这 50 个值不是真值，任何依赖它的后续逻辑都会失效。

另注意一个细节：42 个 FLAC 的合成值是按 `format='mp3'` 算的（因为 `detail` 记录里 format 恒为 `mp3`，取 detail 时还不知道最终容器）。如果将来改成本地 `format`，这 42 个值会整体变化——**不具有向后兼容性**。

**最小复现**

```
node verify/_probe-docid2.mjs
# 期望看到：命中任一合成公式 50/52，按配方拆分 synthetic(mp3)=42 / synthetic(meta.format)=8 / 真实=2
```

## 6. 验证过程中被我自己纠正的误报（诚实记录）

为避免误导，列出我一度判错、后经复核推翻的项——这些**不是**被审计方的缺陷：

| 一度报告 | 实际原因 | 结论 |
| --- | --- | --- |
| 「5 个文件没有 163key → FAIL」 | 是项目的**策略性跳过**，不是漏执行 | 改为与匹配策略审计分流处理 |
| 「G-DRAGON 等 5 个 MP3 尾部标签结构变了」 | 我在比对时用了**偏移量**做相等判断，而文件变大后偏移本来就会平移 | 改为比对「种类+长度+字节内容」，全绿 |
| 「阴雨天/颜人中 MP3 时长差 15s/20s」 | 我的帧走查把采样率**写死 44100**，而这两个文件是 **48 kHz** | 改为从首帧头读采样率 + 用 Xing 权威帧数，Δ 降到 40–47 ms |
| 「心底的旧.mp3 收尾差 583 字节」 | 是**源文件编码器**写的 `Info.bytes` 本身就比实际音频区长 583 字节（备份与原始素材同样如此） | 与打标签无关，改为「与备份一致」断言 |
| 「3 个文件歌手不一致」 | 我的分隔符集合漏了 `;`（ID3 与 Vorbis 实测都用分号） | 补上后全绿 |
| 「FLAC 重复写入不是不动点 → FAIL」 | 混淆了「字节是否变」与「是否报告 noop」两件事：字节确实不变，只是报告语义不一致 | 拆成两条断言，字节幂等通过，报告语义单列为 P2-1 |
