# 匹配质量：踩过的坑与最终判据（Lead）

记录匹配环节的完整排查过程。**这段是给将来维护的人看的**——匿名搜索的行为很反直觉，
不知道这几个坑会反复踩。

## 结论速览

| 判据 | 作用 | 依据 |
|---|---|---|
| **搜索深度 100** | 让原唱进入候选池 | 前 10 条永远全是翻唱 |
| **时长 ±5s 容差** | 排除伴奏 / remix / 现场版 | 同一首歌不同版本时长差 15~30s |
| **专辑名比对** | 从同一录音的多个重复条目里挑出原专辑版 | 精选集版时长只差 1ms，只有专辑名不同 |
| **artist.id === 0 且无专辑** | 识别 UGC 冒充条目 | 上传者没有艺人页，反查是 `周杰伦#0` |

按这套判据在 57 个真实文件上的结果：**自动应用 52 个，人工复核 5 个，P0 错配 0 个**。
（对照：只用「歌名+歌手」打分时，正确率不到一半。）

## 坑 1：匿名搜索是 UGC 优先，原唱埋在深处

`s=简单爱 周杰伦&type=1`，前 10 条长这样：

```
王大毛              - 简单爱 (青涩版)
QK ON THE BEAT      - “简单爱” 周杰伦 Sweet Pop Beat
陈年.Tŋ             - 简单爱
洛淮枳              - 简单爱
周杰伦♚             - 我爱你          ← 名字带音乐符号，是假号
WEICHENG-BEAT       - 周杰伦“简单爱” hip-pop beat
```

**一个真·周杰伦都没有。** 搜索深度与命中数的关系（实测）：

| limit | 结果数 | 其中真·周杰伦(6452) |
|---|---|---|
| 10 | 10 | **0** |
| 30 | 30 | 1（第 21 条，还是现场版） |
| 100 | 100 | 32 |

- 五个端点（`GET/POST /api/search/get/web`、`POST /api/cloudsearch/pc`、`GET/POST /api/search/get`）
  返回**逐字节相同**的结果集 ⇒ 不是端点选择问题。
- 曲库没被封：`type=100` 搜「周杰伦」第一条就是 `6452`；`song/detail` 匿名可查。
- `songCount` 会随 `limit` 变化（limit=30 时 80，limit=100 时 140），**不能当真实总数用**。

## 坑 2：同一录音散落在多个精选集，时长几乎一样

本地 `周杰伦 - 简单爱.flac`：专辑《范特西》，270987ms。depth=100 里 5 个真·周杰伦条目：

| id | 专辑 | duration | Δ |
|---|---|---|---|
| **186119** | **范特西** | 270000 | 987ms |
| 5255440 | K情歌2 | 270986 | **1ms** |
| 421563776 | K情歌10 | 270986 | 1ms |
| 400581054 | 婚礼歌手 | 270986 | 1ms |
| 5249545 | 单.恋 | 270986 | 1ms |

**纯靠时长会挑错**（Δ1ms 的那几个更像）。是**专辑名**把 186119 挑出来的。
所以读取本地专辑标签很重要，`scoreCandidate` 里 album 权重虽然只有 0.05，在这个场景里是决定性的。

## 坑 3：UGC 会直接把艺人名写成「周杰伦」冒充原唱

「爱在西元前 周杰伦」前 100 条里，`artist.id === 0` 的有 25 条，其中 8 条署名「周杰伦」：

```
2153879235  爱在西元前             周杰伦#0   《》            234280ms   ← 冒充
2165576775  爱在西元前 (网友改编)    周杰伦#0   《》            230687ms   ← 冒充
2154256926  爱在西元前 (KTV版伴奏)   周杰伦#0   《》            232698ms   ← 冒充
```

真条目是 `186114 周杰伦#6452《范特西》234253ms`。

**判别特征**：`artist.id` 明确给了且**全是 0**，**且**专辑名为空 ⇒ `isDefiniteUgc()`。
真曲库艺人一定有非 0 id（周杰伦=6452、颜人中=31376161、黄龄=7890）。

### 边界：部分 id 为 0 的不能误伤

`2735941345` 反查是 `pro#53262224/陈小满#0`《心底的旧》——有真艺人、有专辑、时长也对，
是真条目。所以 `isDefiniteUgc` 要求**所有** id 都为 0；
`catalogScore` 里只把「部分为 0」从 1.0 扣到 0.5，不影响排序结果。

## 坑 4：`ambiguous` 判太宽会误杀正确匹配

一开始 `ambiguous = gap < 0.05`，结果 8 个**正确**匹配被打成「需人工复核」：

- 夜曲 `185904《11月的萧邦》`(album=0.57) vs `406346134`(album=0)，分差 0.028 —— 专辑名明明决出了胜负
- 珊瑚海 `185920《11月的萧邦》` vs `406347109`，同理

改成必须**同时**满足：歌名≥0.97、歌手≥0.9、双方时长都在容差内、专辑分差<0.1、总分差<0.05。
只有「四项全 1.0、分数也全等」的真重复条目（如 `拼图爱 2655850235` vs `2659361593`）才算歧义。
这一改让自动应用从 49 涨到 52。

## 坑 5：`verify` 把策略性跳过当成故障

`apply` 默认只写 auto，剩下的标 `skip:needs-review`。但 `verify` 原来只要发现文件没 key 就报错，
于是每次跑都刷 5~8 条「没有 163key」的假警报，真问题被淹掉。

修正：只有两种情况算问题 —— ① 报告里根本没这条记录；② 报告标了 `auto` 却没写上。
其余记作 `intentionally-skipped`，输出里单列一行计数。

## 坑 6：测试不能依赖工作副本的状态

`test/tags.selftest.mjs` 原来从 `E:\CloudMusic_163key` 取「无 key 的样本」来验证写入。
真实写入 52 个文件后，这个假设失效，测试假失败（「FLAC 写入前没有 163key」✗）。

修正：测试一律从**备份** `E:\CloudMusic_backup_20261022` 取输入——它永远保持原始状态。

## 可复跑的审计

`node test/audit-report.mjs out/matches-v4.json`

把报告里每条 auto 的 musicId 拿去 `song/detail` 反查，核对歌名/歌手/专辑/时长，
并专门检查 UGC 冒充。**退出码 0 才允许执行 `apply --write`**。当前结果：

